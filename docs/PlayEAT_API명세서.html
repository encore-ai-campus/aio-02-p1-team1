OpenAPI 기반

1

OpenAPI 우선

두괄식 요약

평가자가 문서의 충족 상태를 먼저 확인할 수 있도록 3개 평가기준과 현재 문서의 근거를 맨 앞에 요약합니다.

1
✓ 대체로 충족

리소스 중심 URL과 HTTP Method 사용

Restaurants, Users, Conversations, Admin 등 리소스 단위로 엔드포인트가 구성되어 있고 GET·POST·PATCH·DELETE가 조회·생성·수정·삭제 의미에 맞게 사용됩니다.

예: GET /restaurants 조회, POST /conversations 생성, PATCH /users/me 부분 수정, DELETE /admin/restaurants/{restaurant_id} 비활성화 처리.

2
△ 부분 충족

표준화된 에러 응답과 4xx/5xx 예외 처리 규칙

검증 오류에 대한 422 HTTPValidationError는 다수 Operation에 정의되어 있으나, HTTP Status Code + 에러 코드 + 메시지 + 상세를 공통 구조로 묶은 표준 에러 모델과 전체 4xx/5xx 규칙은 OpenAPI에서 확인되지 않습니다.

따라서 현재 문서는 OpenAPI에 실제 명시된 비-2xx 응답만 기록하며, 정의되지 않은 401·403·404·409·500 등을 임의로 추가하지 않습니다.

3
△ 부분 충족

Request/Response Pydantic 모델 명확성 및 nested 모델

Request 모델은 필수/선택 여부, 타입과 주요 제약을 확인할 수 있고 LogSummaryRequest.filters → LogFilters처럼 중첩 JSON도 nested 모델로 표현됩니다.

다만 다수 성공 Response가 {}로 스키마 미정의 상태이며, 필드별 example/examples도 확인되지 않아 Response 모델과 예시값 문서화는 보완이 필요합니다.

요약: 평가기준 1은 대체로 충족하며, 평가기준 2·3은 현재 OpenAPI 기준으로 부분 충족입니다. 아래 본문은 기존 API 명세 내용을 변경하지 않고 상세 근거를 제공합니다.

2

문서 작성 기준

  • Endpoint, Method, Parameter, Request Body, Response, Schema, Security는 최종 OpenAPI 값을 기준으로 합니다.
  • OpenAPI에 없는 오류 응답은 임의로 추가하지 않습니다.
  • Endpoint/Schema의 description은 문서에 반영합니다.
  • 성공 Response Schema가 {}이면 스키마 미정의로 표시합니다.

표 읽는 방법

  • 한 API에 요청 항목이 여러 개 있으면 ↳ 행으로 이어집니다.
  • 요청 위치는 Path / Query / Header / Body를 구분합니다.
  • Body는 Pydantic 모델명을 표시하며 세부 필드는 4번 모델 표에서 확인합니다.
  • Response는 OpenAPI의 2xx 응답과 Schema를 표시합니다.
  • 예외처리는 OpenAPI에 명시된 비-2xx 응답만 표시합니다.

  • GET /api/v1/admin/summary-evaluation-runs/{run_id}: 품질평가 실행 결과를 조회한다.
  • POST /api/v1/admin/improvement-experiments: 요약 개선 실험을 등록한다.
  • GET /api/v1/admin/improvement-experiments/{experiment_id}: 개선 실험과 연결된 평가 실행을 조회한다.
